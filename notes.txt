# Baichuan-to-ONVIF/RTSP Bridge for UniFi Protect — Project Notes

## Why this exists
Reolink cameras' own RTSP/ONVIF stream is unreliable for continuous NVR ingestion -
stalls, dropped frames, desync - especially on the sub/low profile. The Baichuan protocol
(TCP/9000, proprietary, reverse-engineered, used internally by the official Reolink
app/NVR) is much more stable. Goal: bridge Baichuan -> standard RTSP + ONVIF so **UniFi
Protect** can adopt these cameras as clean third-party devices, with real motion/smart
detection events, not a degraded "generic RTSP camera."

UniFi Protect specifically requires:
- A stable, compliant RTSP stream.
- Each camera to appear as a distinct ONVIF device on its own port. This does NOT require
  macvlan / real L2 MAC spoofing - all virtual ONVIF devices share the host's/container's
  one real IP, only the port differs per camera, and the "MAC address" Protect cares about
  is just a value reported inside ONVIF GetDeviceInformation/GetNetworkInterfaces, not an
  actual network-layer MAC.
- ONVIF motion/smart-detection events. Protect does NOT run its own AI/motion analysis on
  third-party ONVIF cameras - it is entirely dependent on events pushed/pulled over ONVIF.

## Origin: fork of `Shareed2k/reolinkproxy`
Started (2026-07-15) as a fork rather than a from-scratch reimplementation, to reuse its
mature Baichuan TCP client (login/crypto/video/audio/motion) and gortsplib-based RTSP
server. The project has since diverged substantially from upstream - see "How the plan
changed" below.

## How the plan changed since the original spec
The original spec (see git history) planned to hand-generate ONVIF Media2 profile/encoder
XML per camera, and to eventually add local object-detection inference (ONNX/YOLO) as a
"smart events" substitute. Neither happened as planned:

1. **Hand-rolled ONVIF XML -> transparent reverse proxy.** Getting every camera
   model/firmware's Media2 response (profiles, encoder configs, capabilities) byte-for-byte
   right by hand-generating XML was a losing battle against real-world firmware quirks.
   Replaced with a transparent reverse proxy: `GetProfiles`/`GetStreamUri`/etc. requests are
   forwarded verbatim to the camera's *own* ONVIF Media2 service, re-signed with real
   credentials, and only the RTSP URI in the response is rewritten to point at this proxy.
   Every other field an NVR might depend on matches the physical camera exactly, because it
   comes from the physical camera. ONVIF Device/Events services remain proxy-native (they
   need per-camera identity/port that the real camera doesn't have).
2. **No local object-detection needed - cameras already emit it.** Live testing showed a
   real camera's ONVIF PullPoint feed emits proper smart-detection topics
   (`tns1:RuleEngine/MyRuleDetector/{PeopleDetect,VehicleDetect,DogCatDetect,Package,...}`)
   that its static `GetEventProperties` response never advertised. So `onvifclient.go`
   subscribes to the camera's own events service and forwards every notification into this
   proxy's per-camera event broker verbatim - Protect gets real smart events without any
   local inference. The originally-planned ONNX/YOLO phase is shelved indefinitely; revisit
   only if a camera model turns out not to expose this itself.
3. **Baichuan client bug + RTSP pacer rewrite (stability, not scope).** Live testing on a
   real Protect instance surfaced stutter/freezes on the sub/low stream that did not
   reproduce in VLC/ffprobe (which mask jitter with their own buffering; Protect doesn't).
   Root-caused to four distinct bugs: (a) Main's high message volume could starve Sub's
   shared Baichuan subscriber channel (fixed via per-StreamType dispatch), and (b) three
   separate scheduling bugs in the RTSP media pacer's wall-clock model (an off-by-one in
   which item's duration drove the next emission time, a self-inflicted stall from
   restoring latency cushion on the wrong branch, and a latency-inflation feedback loop).
   All four fixed and confirmed via live diagnostics (zero deviation events over a 75s
   window, down from firing on nearly every frame).
4. **Web UI + persisted config added, not originally scoped.** Env-var-only config didn't
   scale to add/edit/remove-camera workflows or runtime visibility, so a YAML config store
   (`configstore.go`) plus a status/config web UI (`webui.go`) were added: camera CRUD,
   live per-camera status (connected/reconnects/last error, RTSP client count, bitrate,
   event-forwarder health, 24h event count), a scrollable events log with human-readable
   topic names, adjustable log level with a live log viewer, and server stats (uptime,
   memory, goroutines, GC runs). `REOLINK_*` env vars now only *bootstrap* the config file
   on a first run; the file (editable by hand or via the web UI) is authoritative after
   that for cameras **and** for `mqtt`/`server`/`onvif` global settings.
5. **NVR-specific "Protect connected" status removed.** An earlier iteration added a
   dedicated "is UniFi Protect reachable" indicator (`SERVER_PROTECT_IP`). Removed by
   request - the web UI shows generic per-camera/event-forwarder health instead, without
   assuming which specific NVR is consuming the stream.

## Current architecture (high level)
- `pkg/baichuan`: Baichuan TCP client - login/crypto, video/audio streaming (per-StreamType
  subscriber dispatch), motion listener, talkback.
- `cmd/reolinkproxy/pacer.go`: wall-clock media pacer that smooths bursty Baichuan delivery
  into steady RTP timing before it reaches gortsplib.
- `cmd/reolinkproxy/onvif.go`: per-camera virtual ONVIF Device/Events service, plus a
  transparent Media2 reverse proxy to the camera's own ONVIF service (rewrites only the
  RTSP URI).
- `cmd/reolinkproxy/onvifclient.go`: subscribes to the camera's *own* ONVIF events service
  and forwards its real notifications (motion + smart detections) into the proxy's event
  broker.
- `cmd/reolinkproxy/wsdiscovery.go`: one shared UDP 3702 WS-Discovery responder, replying
  once per configured camera with a stable device UUID.
- `cmd/reolinkproxy/configstore.go` + `webui.go`: persisted YAML config (`config.yml`) and
  the status/config web UI - camera CRUD, live status, events log, server stats, log
  viewer.
- Docker: `network_mode: host` is the recommended deployment (WS-Discovery multicast,
  Reolink UID broadcast discovery, and per-camera auto-assigned ONVIF ports all need open
  host-level networking); see README.md for the bridge-mode port list if host networking
  isn't an option.

## Status
Validated end-to-end against real Reolink camera hardware: Baichuan login/video/audio,
RTSP playback, per-camera ONVIF Device/Media/Media2 (byte-for-byte via the reverse proxy),
WS-Security auth, ONVIF Events/PullPoint round-trip, real snapshot proxying, config
persistence through the web UI's HTTP API, and self-restart from the web UI. The pacer/
Baichuan stability fixes were confirmed against live UniFi Protect playback specifically
(the original motivating use case), not just generic RTSP clients.

## Still open / not started
- Docker image published to a registry (currently build-from-source only, see README.md).
- Broader validation across more Reolink camera models/firmware versions than the ones
  tested so far - the transparent-reverse-proxy approach should generalize well, but
  quirky firmware could still surface model-specific edge cases.
